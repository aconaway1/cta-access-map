# CLAUDE.md — Step Free Chicago Transit

Context handoff from a claude.ai chat (2026-10-11). Read this before touching the code.

## What this is

A Cloudflare Worker with static assets: a Leaflet map of every CTA 'L' station (systemwide since 2026-10-11)
showing elevator access, line colors, Loop direction of travel, live elevator outages and step-free alternatives.
Downtown (Loop, West Loop, River North) is hand-maintained and detailed; the rest is generated from open data. Static site +
a small Worker for the API, `*.workers.dev` subdomain, no custom domain, no build step. The owner's older
projects (ronconrails.com, the CML Springfield schedule map) are on Pages, but Cloudflare now treats Pages as
legacy ("applications" are Workers), so this one is a Worker; don't suggest Pages.

Owner: Aaron (network engineer). Prefers direct, technically precise communication.

## Files

- `public/` — the static site (`[assets] directory`; the assets layer serves these before the Worker runs):
- `public/index.html` — page shell, collapsible key panel (auto-collapsed under 600px width)
- `public/style.css` — light/dark via `prefers-color-scheme`
- `public/cta-data.js` — GENERATED by `scripts/build_data.py`; don't edit. `CTA_DATA = {generated, stations, lines}`:
  all 144 stations (id = map ID, name, ll, k, lines, generated `alt`) and GTFS track pieces outside downtown.
- `scripts/build_data.py` — stdlib-only Python; downloads the city L stops dataset and CTA GTFS into `.cache/`
  (gitignored, GTFS is ~70 MB) and writes `cta-data.js`. Rerun after CTA schedule/renovation changes, review
  its "ADA mismatch" notes, commit the output. Reads downtown IDs, names and closures from `app.js`.
- `public/app.js` — `DOWNTOWN` hand-maintained stations (override generated ones by ID, field by field; plus a
  Roosevelt position override), `STATIONS` = merged list, `METRA` downtown stations, `TRACKS` geometry, map setup, pixel-offset track rendering, alert polling (5 min) with stale indicator, step-free alternatives (`alt`), locate-me control (watchPosition; position stays client-side) with a nearest-accessible-stations card
- `src/worker.js` — Worker entry; routes `GET`/`HEAD /api/elevators`, 405 for other methods, 404 for anything else
- `src/runlog.js` — `RunLog` Durable Object: per-request log of Metra fetches (see Metra section)
- `src/metra.js` — `GET /api/metra-alerts` and `/api/metra-log.csv`; Metra GTFS-realtime alerts (protobuf → JSON) using the `METRA_API_TOKEN` secret
- `src/elevators.js` — `GET /api/elevators`; proxies CTA Customer Alerts API
  (`accessibility=TRUE&activeonly=TRUE`, JSON), normalizes to `{updated, alerts:[{id,headline,short,stations:[{id,name}]}]}`, 120s cache
- `README.md` — deploy and dev commands (`npx wrangler deploy`, `npx wrangler dev`)

CDNs: Leaflet 1.9.4 (cdnjs), leaflet-polylinedecorator 1.6.0 (unpkg), Tabler icons webfont (jsdelivr).
Basemap: Stadia Maps alidade_smooth / alidade_smooth_dark (CARTO now requires an API key). Production
needs the workers.dev hostname registered in the Stadia dashboard. `wrangler.toml` holds name, output dir, compat date.

## Track geometry and direction (verified)

- Loop rectangle: Lake (N), Wabash (E), Van Buren (S), Wells (W). Corners `NW/NE/SE/SW` in `app.js`.
- Brown: counterclockwise, Outer Loop. Enters/exits at Tower 18 (NW) via Wells.
- Orange, Pink, Purple Express: clockwise, Inner Loop. Orange enters at Tower 12 (SE) from Roosevelt;
  Pink enters at Tower 18 from the west on Lake; Purple at Tower 18 from the north.
- Loop stop orders. `alt` means "use this station instead" (works in either direction), so Loop entries give
  distance + which lines stop there, never "next stop"; a one-way line can't ride back. Every `alt` entry starts with an
  approximate distance (street grid; straight line +15% along diagonal Milwaukee Ave), computed from the city
  dataset coordinates and baked into the strings. Orders, for reference:
  - Brown (outer, CCW): Mart → Washington/Wells → Quincy → LaSalle/Van Buren → HWL → Adams/Wabash →
    Washington/Wabash → (State/Lake) → Clark/Lake → Mart
  - Purple (inner, CW): Mart → Clark/Lake → Washington/Wabash → Adams/Wabash → HWL → LaSalle/Van Buren →
    Quincy → Washington/Wells → Mart. Pink: same loop, entering and leaving via Clinton (Green/Pink).
  - Orange (inner, CW): Roosevelt → HWL → LaSalle/Van Buren → Quincy → Washington/Wells → Clark/Lake →
    Washington/Wabash → Adams/Wabash → Roosevelt
  - Green (both ways): Clinton ↔ Clark/Lake ↔ Washington/Wabash ↔ Adams/Wabash ↔ Roosevelt
- Arrows only on the Loop-circling lines (Brown, Orange, Pink, Purple). Green, Red and Blue run both ways and
  get one line with no arrows, the owner's call (2026-10-11).
- Brown/Purple north branch (`N_BRANCH`): Wells across the river past Merchandise Mart, jog to Franklin at
  Hubbard, north on Franklin past Chicago Ave (map edge ~41.9005).
- Red: subway under State (dashed), north to past Chicago Ave. Blue: subway under Dearborn, west along Congress;
  at-grade in the Eisenhower median west of the river (solid); north end under Lake then northwest under
  Milwaukee past Grand and Chicago.
- `d` in `TRACKS` is a pixel offset to the right of travel direction; `offsetPath()` recomputes miter
  offsets in layer-pixel space on every `zoomend`, and arrow decorators are rebuilt with it.
  Closed paths (first point == last) are handled for the rectangle.
- Coordinates are approximate (hand-placed), good enough for a schematic, not survey-grade.

Researched for the accessibility follow-up:
- Static GTFS is public, no key: `https://schedules.metrarail.com/gtfs/schedule.zip` (check `published.txt`).
  `stops.txt` has `wheelchair_boarding` (196 × `1`, 45 × `0` = unknown, none `2`). It disagrees with Metra's
  elevator list (79th/Chatham, 87th/Woodruff, 103rd/Rosemoor, Grand/Cicero are `0` but have elevators;
  Millennium is `1` while its only elevator is closed until winter 2026–27), so overrides are needed.
- Realtime: `https://gtfspublic.metrarr.com/gtfs/public/alerts` (protobuf, 30s refresh). Key approved 2026-10-12,
  stored ONLY as the Worker runtime secret `METRA_API_TOKEN` (Settings → *Runtime variables and secrets*, the
  section above Bindings, not the Builds one; not in wrangler.toml, not in the repo). The owner chose to test
  against the CF deployment rather than keep a local `.dev.vars` copy (gitignored anyway); locally the endpoint
  returns 503 and the UI hides the Metra list. Don't ask for the key or read `.dev.vars`.
- `src/metra.js` → `GET /api/metra-alerts`: Bearer header + User-Agent, token trimmed. A bad/missing key gets
  401 `{"message":"Unauthenticated"}` from IIS. Intermittent 403s (about 1 in 3 requests, in ~30 s runs) come
  from Metra's Azure Application Gateway WAF, not the API, and hit header and `?api_token=` forms alike, so the
  Worker retries once after 1.5 s and then serves the isolate's last good response (<15 min, `cached:true`,
  Metra's own `updated` time kept). The page retries a failed first load after 30 s.
  Superseded Oct 12 evening (block rate reached ~50%): a Cron Trigger every 5 min (`[triggers]` in wrangler.toml)
  runs `refreshMetra()`, up to 4 tries 45 s apart, and stores the last good copy (plus `fetched`) in KV namespace
  `cta-access-map-cache` (binding `CACHE`, id in wrangler.toml; not secret). `/api/metra-alerts` serves the KV
  copy; one live fetch only if KV is empty. Writes only on success (≤288/day, free plan allows 1,000). The page
  marks Metra data older than 30 min "may be out of date". Owner chose 5 min (fresh enough; 10 would compound
  blocked runs). Don't use the KV page's "Connect" button: bindings must live in wrangler.toml or deploys drop them.
  If blocking persists, ask Metra to allow Cloudflare Workers egress.
- `scheduled()` AWAITS refreshMetra; the first version used ctx.waitUntil, whose ~30 s post-return budget killed
  runs during the 45 s retry wait, so the stored copy never refreshed.
- Page-visit refresh (owner's call, Oct 12): `/api/metra-alerts` returns the KV copy immediately; if it's >5 min
  old it makes ONE background attempt via ctx.waitUntil (fits its ~30 s), max once per isolate per 2 min, recorded
  in `metra-runs` with `source:'visit'` (scheduled runs `source:'cron'`). Reason: the first fixed cron run (8:30 PM)
  got 403 on all 4 attempts while visitor-colo requests got through ~50%.
- `/status` (public/status.html + `GET /api/status`, src/status.js): live CTA feed check, Metra saved copy age and
  counts, the Metra request log, deployed version (`[version_metadata]` binding CF_VERSION), station data counts.
  Public by the owner's choice; shows only whether keys are set.
- Metra request log (Oct 13): every individual request to Metra (scheduled and page-visit) is a row in a
  SQLite-backed Durable Object (`RunLog`, src/runlog.js, binding `RUN_LOG`, migration in wrangler.toml; free plan),
  kept 8 days: time, source, run, try number, HTTP status, ms, Cloudflare colo (visits: `request.cf.colo`; cron:
  `/cdn-cgi/trace`), Server header and Metra's `x-ratelimit-*` (limit 200; seen on 401s from IIS), whether the body is Azure Application Gateway's error page. Never the body or
  anything with the key. `/api/metra-log.csv` downloads it. Replaced the KV list `metra-runs`, which lost runs when a
  cron run and a visit wrote at once (7:15–7:35 AM Oct 13); that list was imported once with reconstructed per-try
